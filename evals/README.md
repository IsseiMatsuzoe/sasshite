# 比較試験

## 問い

通常の応答と比べて、伝達内容を選ぶ判断を促すことに追加の効果があるか。簡潔さを求める短い指示と比べても利点があるか。必要な詳しさ、留保、確認、対話の柔軟さを失っていないか。

この試験は応答内容の診断であり、人間の認知負荷の直接測定ではない。

## 入力と条件

- `cases.jsonl`: 12個の合成会話。各ケースは user / assistant / user の固定履歴で、最後の user への次の応答を生成する。
- `rubric.json`: 評価専用。ケース別の必要な内容、失敗条件、共通の判断基準を含む。生成側には渡さない。
- `runs/2026-11-25-pilot/conditions/`: 初回試験に使用した、変更しない指示のスナップショット。

| 条件 | 追加する指示 |
|---|---|
| baseline | なし。ホスト共通の指示は残る |
| concise | 関連性、簡潔さ、明瞭さ、必要な正確さと説明を求める短い指示 |
| sasshite | 試験時点の `SKILL.md` 全文 |

| ケース | 確かめる内容 |
|---|---|
| C01 | 相談の目的と制約に沿う判断 |
| C02 | 解決策を求めていない対話への具体的な応答 |
| C03 | 既知の基礎説明に戻らず、誤った推論に不同意を示す |
| C04 | 第三者向けの報告で完了・未確認・未実施を残す |
| C05 | 既に表にある数値から関係を説明する |
| C06 | 削除対象を確定するために必要な確認をする |
| C07 | 初見の読者に向けた詳しい説明と、重要な限界の保持 |
| C08 | 訂正された条件を適用し、指定の表だけを返す |
| C09 | 未知と否定を区別し、指定の JSON だけを返す |
| C10 | 条件を照合して指定の一語だけを返す |
| C11 | 物語の解釈を根拠づけ、不要な留保や助言に逃げない |
| C12 | 争点を説明し、まだ依頼されていない制度選択をしない |

## 初回の実行条件

同じ親モデル・設定を引き継ぐ、履歴を共有しない新しいサブエージェントを条件ごとに一つ起動した。各エージェントには、その条件の指示と12会話のみを渡した。同じ順序で、一つのバッチとして各ケースに回答した。

したがって条件間の履歴は独立しているが、同じ条件内の12件がそれぞれ独立した API 呼び出しになっているわけではない。API モデル ID、sampling 設定、ケース単位のレイテンシやトークン数はツールから取得していない。単一回の診断として扱う。適用の自動判定も対象外である。

試験前に入力と Skill の SHA-256 を記録した。出力を見てから採点基準を変えたり、失敗した回答を差し替えたりしない。修正後の再試験は別の run として残す。

## 再実行の準備

比較用スクリプトは Python 標準ライブラリだけで動く。以下はリポジトリのルートから実行する。モデルへの依頼自体は、利用するホストで行う。

```bash
python scripts/evaluate.py prepare \
  --cases evals/cases.jsonl \
  --conditions evals/runs/2026-11-25-pilot/conditions \
  --out evals/local/new-run/packets \
  --seed 20261125
```

条件ごとの packet を新しい会話に渡し、そこで指定された JSONL を `responses/<condition>.jsonl` に保存する。各 `response` は実際の返答全体である。JSONL は保存用の外枠であり、回答本文の形式を指定するものではない。

出力先が存在するとスクリプトは停止する。再試験では新しいディレクトリを使う。

## 条件を隠して評価する

```bash
python scripts/evaluate.py blind \
  --cases evals/cases.jsonl \
  --rubric evals/rubric.json \
  --responses evals/local/new-run/responses \
  --out evals/local/new-run/blind \
  --seed 20261126
```

評価者には `blind/packet.json` **だけ**を渡す。条件名、指示文、元の回答ファイル名を含まない。`private_key.json` は評価の終了後に集計に使う。ラベルと順序はケースごとに割り振られる。

各回答の採否と具体的な問題点を記録し、同じケースの候補から意味上最も適するものを選ぶ。実質的な差がなければ複数または全候補を同率にする。短さ、見出しの数、丁寧さそのものでは選ばない。ユーザーが明示した形式だけは遵守を確認する。

```bash
python scripts/evaluate.py summarize \
  --judgments evals/local/new-run/judgments.json \
  --key evals/local/new-run/blind/private_key.json
```

集計は合格数、単独で選ばれた数、同率で選ばれた数を示す。未選択候補同士の優劣は分からないため、その組を同率に数えない。文字数は診断として別に表示し、得点にはしない。

明示された JSON と一語の条件は、別途機械的に確認できる。

```bash
python scripts/check_contracts.py --responses evals/local/new-run/responses
```

この検査は C09・C10 の指定だけを対象とする。他の回答の形式は制限しない。

## 解釈

LLM 評価者の判断は、利用者の実感の代わりにはならない。人間が条件名を隠した候補を読み、実際に必要だった説明や余計だった箇所を確かめると、次の改訂に使える。より強い比較には、ケース単位の独立呼び出し、複数回の生成、実際の長い対話、モデルと設定の記録、人による評価が必要になる。

入力、回答、評価を残して、効果が見られなかった条件や欠落も確認できるようにする。まずは [初回結果](runs/2026-11-25-pilot/RESULTS.md) を参照。
